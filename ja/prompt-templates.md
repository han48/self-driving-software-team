# プロンプトテンプレート – 各フェーズ向けAIプロンプトテンプレート

> 以下のテンプレートを使用して、AIにプロセスの正しいフォーマットで出力を生成させてください。
> `{...}` を実際の内容に置き換えてください。

---

## 1. 要件生成（Spec）

### 基本プロンプト

```
以下の機能のrequirements.mdを生成してください：

{要件の概要 – 1-2文またはミーティングノートでも可}

要件：
- EARS記法を使用（THE/WHEN/IF + SHALL）
- 各要件にUser Storyを含める
- ハッピーパスとエラーケースの両方をカバー
- 専門用語のGlossaryを定義
- 受入基準に番号を付ける（1, 2, 3...）
- 曖昧さを検出した場合 → QA-XXXを作成
- リスクを検出した場合 → RISK-XXXを作成

出力フォーマット：付録A.2の構造に従う
ファイル場所：openspec/specs/{feature-name}/requirements.md
```

### 上級プロンプト（コンテキスト付き）

```
コンテキスト：
- プロジェクト：{プロジェクト名}
- 技術スタック：{Node.js + PostgreSQL + React...}
- 既存スペック：{関連スペックへの参照（あれば）}
- 制約：{期限、予算、技術的制限}

クライアントからの生の要件：
"{元の要件をコピー＆ペースト}"

requirements.mdを生成してください。注意事項：
- 現在のアーキテクチャと互換性があること
- 既存スペックとの競合を確認
- 契約範囲を超える要件の場合はフラグを立てる
```

## 2. 設計生成

### 基本プロンプト

```
承認済みのrequirements.md（ファイル：openspec/specs/{feature}/requirements.md）に基づき、
以下を含むdesign.mdを生成してください：

1. 概要（技術スタック、アプローチ）
2. サイトマップ（Mermaidグラフ）
3. GUIデザイン（gui/フォルダにHTMLプロトタイプを生成）
4. アーキテクチャ（シーケンス図）
5. データベース設計 + ERD
6. インフラ設計
7. コンポーネント＆インターフェース
8. 正確性プロパティ（プロパティベーステスト用）
9. エラーハンドリング戦略
10. テスト戦略

要件：
- 各コンポーネントは対応する要件を参照すること
- GUIプロトタイプはブラウザで直接開けること
- データベース設計にはインデックス戦略を含めること
- 正確性プロパティは「For any...」形式で記述

出力フォーマット：付録A.3の構造に従う
```

### 小規模機能向けプロンプト（セクション省略）

```
機能サイズ：Small（1日未満）
design.mdは以下のセクションのみ生成：
- Overview
- Components & Interfaces
- Testing Strategy

省略：Site Map、GUI、Architecture、Database、Infrastructure
（機能が小さすぎるため、フルデザインは不要）
```

## 3. タスク生成

### 基本プロンプト

```
承認済みのdesign.md（ファイル：openspec/specs/{feature}/design.md）に基づき、
tasks.mdを生成してください：

要件：
- 各タスク4時間未満の工数
- ネストされたチェックボックス形式（- [ ] 1. / - [ ] 1.1）
- 各サブタスクに _Requirements: X.X_ 参照を含める
- タスク依存関係グラフ（JSON waves）
- コード、ユニットテスト、統合テスト、E2Eテストのタスクを含める
- 論理的な順序：セットアップ → コアロジック → テスト → 統合

出力フォーマット：付録A.4の構造に従う
```

---

## 4. RADIOレポート生成

### 基本プロンプト

```
機能{名前}のRADIOレポートを生成/更新してください：

データソース：
- tasks.md：{X}/{Y}タスク完了
- CI結果：{pass/fail、カバレッジ%}
- ブロッカー：{リスト（あれば）}
- 最近の変更：{最近のコミット}

フォーマット：
- R：ステータス + 具体的なメトリクス
- A：現在のタスク + 次のステップ
- D：ブロッカー/リスク（または「None」）
- I：進捗に影響するコンテキスト（または「—」）
- O：達成した結果 + 数値

深刻なDアイテムがある場合 → RISK-XXX/ISSUE-XXXが存在するか確認し、なければ作成。
```

## 5. バグ修正スペック生成

### 基本プロンプト

```
バグレポート："{バグの説明}"
再現手順：{手順}
期待動作：{期待される動作}
実際の動作：{実際の動作}

以下を含むbugfix.mdを生成してください：
1. 現在の動作（Defect）– EARS形式
2. 期待される動作（Correct）– EARS形式
3. 変更しない動作（Regression Prevention）– EARS形式

次にdesign.mdを生成：
- 5WHY根本原因分析（真の根本原因まで掘り下げる）
- 修正実装（外科的、最小限の変更）
- 変更ファイル（明確な表）
- 予防策（この種のバグが再発しないようにする方法）
- 正確性プロパティ

出力：openspec/bugs/{bug-name}/bugfix.md + design.md + tasks.md
```

## 6. CR（変更要求）評価

### 基本プロンプト

```
新しいCRを受領：
- 送信元：{ソース}
- 説明："{CR内容}"
- 詳細：{箇条書きリスト}

以下を実施してください：
1. 現在のシステムへの影響を評価
2. 工数を見積もり（時間/日）
3. 実装した場合のリスクを評価
4. 優先度を提案（High/Medium/Low）理由付き
5. 既存のスペック/設計との競合を確認
6. backlog.mdの「Pending」セクションに正しいフォーマットで記録
```

## 7. リスク＆課題検出

### リスク検出プロンプト

```
{ファイル：spec/design/code}をレビューしてリスクを検出してください：

確認事項：
- セキュリティリスク（インジェクション、認証バイパス、データ漏洩）
- パフォーマンスリスク（N+1、メモリリーク、タイムアウト）
- スケーラビリティリスク（単一障害点、ボトルネック）
- 依存関係リスク（非推奨ライブラリ、破壊的変更）
- ビジネスリスク（スコープクリープ、不明確な要件）

検出された各リスクについて：
- 確率（H/M/L）+ 影響（H/M/L）を評価
- 予防策を記述（回避するために何をするか）
- 軽減策を記述（発生した場合に何をするか）
- トリガーを特定（警告サイン）

出力：openspec/risk-issue/risks.mdにRISK-XXX形式で追加
```

## 8. Q&A生成

### 曖昧さ検出時のプロンプト

```
スペック/設計を読んでいて、曖昧な点を発見しました：
"{曖昧さの説明}"

以下を実施してください：
1. コンテキストを含む明確な質問でQA-XXXを作成
2. 可能なオプションをリスト（わかっている場合）
3. デフォルトの回答を提案（推論可能な場合）
4. 回答すべき人を特定（クライアント / アーキテクト / リード）
5. 優先度を評価（実装をブロックする場合はHigh）

出力：openspec/qa/QA-XXX/thread.md + index.mdを更新
```

---

## プロンプト使用のヒント

1. **コンテキストは多いほど良い：** 関連ファイルを添付し、説明だけにしない
2. **既存スペックを参照：** 関連するスペックがあれば言及する
3. **制約を明示：** 期限、技術スタック、チームサイズは出力に影響する
4. **反復的に：** 出力が正しくない場合 → 具体的なフィードバックを与え、最初からやり直さない
5. **フォーマットを確認：** AI生成後 → 付録A/Bのフォーマットに合っているか確認
