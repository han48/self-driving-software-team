## 基本原則

> 人間が承認し責任を負う。AIが定義、実行、報告する。

---

## 4つの柱

| 柱 | 役割 |
|----|------|
| **RACI** | 人間とAI間の明確な責任分担 |
| **RADIO** | 標準化されたレポート、AIによる自動化 |
| **Spec** | 唯一の真実の源、AIへの入力 |
| **AIエージェント** | 自動的に実行、検証、報告 |

---

## ワークフローサマリー

```
生の要件 → [AI: Spec] → ✅ 承認 → [AI: Design] → ✅ 承認 → [AI: Tasks] → ✅ 承認 → [AI: Code+Test] → [AI: RADIO] → ✅ 最終承認
```

---

## 主要コンセプト

### AI-FirstモデルにおけるRACI

| 役割 | 定義 | エンティティ |
|------|------|------------|
| **R** – Responsible | 作業を実行 | 🤖 AIエージェント |
| **A** – Accountable | 最終責任 | 👤 人間（リード/PM） |
| **C** – Consulted | 決定前に相談 | AI + 人間 |
| **I** – Informed | 結果を通知 | ステークホルダー |

### RADIO – 進捗報告フレームワーク

| 文字 | 内容 | 説明 |
|------|------|------|
| **R** | Review | Specに対する現在のステータス |
| **A** | Action | 進行中の作業 |
| **D** | Difficulty | ブロッカー、リスク、エスカレーション必要な課題 |
| **I** | Information | 進捗に影響する追加コンテキスト |
| **O** | Outcome | 達成結果、具体的メトリクス |

### テスト戦略 – テストレベル

| レベル | 種類 | 実行者 | タイミング |
|--------|------|--------|-----------|
| L1 | ユニットテスト | AIエージェント | 毎コミット |
| L2 | 統合テスト | AIエージェント | 毎PR |
| L3 | E2E自動化 | AIエージェント | 毎PR / ナイトリー |
| L4 | デスクトップ自動化 | AIエージェント | ナイトリー / リリース |
| L5 | 手動テスト | QA/テスター（人間） | リリース前 |
| L6 | プロパティベーステスト | AIエージェント | 毎PR（オプション） |

### 導入レベル

```
Level 1: AI-Spec+Execute（第1–4週）
Level 2: AI-Managed（第5–8週）
Level 3: AI-Autonomous（第9–12週）
Level 4: AI-Full（第13週以降）
```

### フルプロセスを使用しない場合

| 状況 | アプローチ |
|------|----------|
| 本番ホットフィックス（30分未満） | 直接修正 → PR → 後でドキュメント化 |
| 設定変更 | PR直接 → 承認 |
| タイポ/コピー変更 | PR直接 → 承認 |
| プロトタイプ/POC | requirements.mdのみ（簡潔に） |
| 依存関係更新 | PR + テストパス → 承認 |
| 小さなUI調整 | requirements + tasksのみ |

### Definition of Done

| 成果物 | DoD |
|--------|-----|
| Spec | ✅ 承認済み + ✅ バージョン管理 + ✅ 未解決QAなし + ✅ EARS形式 |
| Design | ✅ 承認済み + ✅ GUIレビュー可能 + ✅ 全requirements網羅 |
| Feature | ✅ 全タスク完了 + ✅ テストパス + ✅ Spec準拠 ≥ 95% + ✅ PRマージ済み |
| Bugfix | ✅ 根本原因確認 + ✅ 修正マージ済み + ✅ リグレッションパス + ✅ 予防策適用 |
